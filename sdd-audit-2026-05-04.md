# SDD-for-SpecForge Audit — 2026-05-04

Evidence-based audit of the SDD system used to develop SpecForge. All conclusions derived from repository files only.

---

## 1. Reconstructed Current Workflow

The actual lifecycle enforced by the system, from idea to closure:

### For `sdd-system`, `tooling/foundation`, and `fix` changes

1. **Classify** — decide change type using criteria in `docs/conventions/spec-change-gating.md §2.1` and `docs/workflows/start-plan.md`.
2. **Create change folder** — `sdd/changes/<change-id>/` (kebab-case slug; date prefix optional).
3. **Create `proposal.md`** — required sections: problem statement, objectives, scope/out-of-scope, risks, success criteria, type (`sdd-system` / `tooling/foundation` / `fix`), status (`Draft`). For `tooling/foundation`: also compatibility assumptions, version pinning justifications, and cross-cutting ownership declarations, per `docs/conventions/tooling-changes.md`.
4. **Proposal review** — human or agent review. No automated gate; discipline only.
5. **Create `tasks.md`** — atomic tasks, verification steps, definition of done, status `Draft`.
6. **Pick up task** — create branch per `docs/conventions/git.md`; mark task `[~]`; set `tasks.md` status to `In Progress`; set `proposal.md` status to `In Progress`. (Workflow: `docs/workflows/start-task.md`.)
7. **Implement** — minimum scope only; update docs in same commit; probe-first for tooling tasks. (Workflow: `docs/workflows/implement-task.md`.)
8. **Mark task complete** — `[x]`; reconcile statuses.
9. **Validate** — run `docs/workflows/validate-docs.md` checklist.
10. **Close** — `tasks.md` → `Complete`, then `proposal.md` → `Closed`.
11. **Open PR** — link change artifacts in description.

### Additional preconditions for `feature` changes

Before step 2:

- A spec must already exist at `sdd/specs/<topic>.md` and must pass all readiness criteria in `docs/conventions/spec-change-gating.md §2.2`.
- Workflow for creating or maturing the spec: `docs/workflows/write-spec.md` (added in this session).
- Proposal must reference the spec: `**Spec reference:** sdd/specs/<topic>.md`.
- At planning time (`start-plan.md`), spec readiness is re-verified before tasks are approved.

### Key gate summary

| Change type | Spec required? | Tooling checklist? |
|---|---|---|
| `feature` | Yes — ready spec must pre-exist | No |
| `tooling/foundation` | No | Yes — `tooling-changes.md` |
| `sdd-system` | No | No |
| `fix` | No | No |

## 2. SDD Compliance Classification

**Classification: Partially SDD-compliant**

### Evidence for compliance

- `spec-change-gating.md` defines a hard spec-first gate for `feature` changes, enforced at both proposal and planning stages.
- Specs in `sdd/specs/` are formally separated from proposals and tasks.
- `docs/conventions/documentation.md` has an explicit spec-reality mismatch rule: stop implementation, revise spec first.
- The spec template requires user-observable behavior (inputs, outputs, side effects, error modes) and testable acceptance criteria — genuine SDD artifacts.
- Change lifecycle enforces docs-in-same-change rule.

### Evidence against full compliance

- `sdd/specs/` contains **no spec files**. The README states "No specs exist yet." The primary SDD gate (spec-first for features) has never been exercised in practice.
- Every actual change to date has been classified `sdd-system` or `tooling/foundation`. No `feature` change proposal exists in the repository.
- `tooling/foundation` and `sdd-system` changes have no spec requirement. These constitute 100% of the change history.
- The feature spec gate is sound in architecture but empirically unvalidated. It is untested infrastructure.
- Enforcement is entirely convention-based (no CI check, no automated gate). Drift relies only on contributor discipline.

### Conclusion

The system is architecturally SDD: it has a spec-first rule, a formal spec layer, and lifecycle enforcement. But the spec layer has never been used. The system functions today as a high-quality change-management workflow with SDD infrastructure waiting to be exercised.

## 3. Consistency Analysis

### 3.1 Status vocabulary violations (concrete examples)

`docs/conventions/change-artifacts.md §3.1` defines valid proposal statuses: `Draft`, `In Progress`, `Closed`, `Superseded`.

| File | Actual value | Canonical value |
|---|---|---|
| `sdd/changes/2026-04-22-define-node-typescript-cli-foundation/proposal.md` | `Draft (proposed)` | `Draft` |
| `sdd/changes/2026-04-22-install-cli-foundation/proposal.md` | `Draft (not started)` | `Draft` |

### 3.2 Type vocabulary violation

`docs/conventions/change-artifacts.md` and `docs/workflows/start-plan.md` define canonical types: `feature`, `tooling/foundation`, `sdd-system`, `fix`.

| File | Actual value | Canonical value |
|---|---|---|
| `sdd/changes/2026-04-23-strengthen-tooling-change-workflows/proposal.md` | `SDD system improvement (no application code changes)` | `sdd-system` |

### 3.3 Closure rule violation

`docs/conventions/change-artifacts.md §5` states: `proposal.md` must be set to `Closed` after `tasks.md` is `Complete`.

| Change | `tasks.md` status | `proposal.md` status | Violation |
|---|---|---|---|
| `2026-04-22-install-cli-foundation` | `Complete` | `Draft (not started)` | Yes — proposal not closed after tasks complete |

### 3.4 Tasks file missing status field and incomplete definition of done

`sdd/changes/2026-04-22-define-node-typescript-cli-foundation/tasks.md`:
- No `**Status:**` header field.
- All definition-of-done items are `[ ]` (unchecked), despite the work being demonstrably complete (referenced files exist in the repository).
- This creates an ambiguous state: tasks were executed but the file was not formally closed.

### 3.5 `docs/features/_template/plan.md` vs `tasks.md` overlap

`docs/features/_template/plan.md` contains a `## Tasks` section with task-item checkboxes. This duplicates the role of `tasks.md`. Since `change-artifacts.md` now mandates `tasks.md` as the canonical execution tracker, the plan template's task section is redundant. `docs/workflows/start-plan.md` still instructs contributors to create `docs/features/<feature-name>/` from this template, which perpetuates the duplication.

### 3.6 `validate-docs.md` checklist ambiguity

Item: "Any new or modified behavior is reflected under `docs/features/`."

This item does not specify when it applies. `sdd-system` changes do not add features, but the checklist applies to all changes. A contributor following the checklist for an `sdd-system` change would have no basis for skipping this item. In practice, every `sdd-system` change closed without a `docs/features/` entry and the checklist was apparently satisfied anyway — but the criterion is ambiguous.

### 3.7 Status rules defined in three places

Status relationship rules appear independently in:
- `docs/conventions/change-artifacts.md §4`
- `docs/workflows/start-task.md`
- `docs/workflows/implement-task.md`

The rules are currently consistent. But they are duplicated, which means a future edit to one without the others creates drift. The convention document is not explicitly designated authoritative in the workflow docs.

### 3.8 `README.md` "Target stack" section

`README.md` says "Target stack: Node.js + TypeScript / pnpm." This mixes the implementation stack with target-stack vocabulary. `docs/conventions/target-stack.md` explicitly separates these two concepts. However, since `node-typescript` is also the dogfooding preset, this may be intentional shorthand rather than a real conceptual error.

## 4. Operational Usability Assessment

### Can a contributor correctly decide when to create a spec?

**Yes, for new contributors.** `spec-change-gating.md §2.1` provides explicit inclusion/exclusion criteria with a mixed-case rule. `start-change.md` step 1 enforces the gate. The criteria are clear and objective.

**Weak point:** classification judgment is still required at the boundary of `fix` vs `feature` (where a fix also expands behavior). The rule is stated but requires reading both `spec-change-gating.md` and `start-change.md`.

### Can a contributor know how to create a spec?

**Yes, now.** `docs/workflows/write-spec.md` was added in this session. Before this session, no such workflow existed — this was the primary gap in the spec authoring path.

### Can a contributor know when a spec is ready?

**Yes.** `spec-change-gating.md §2.2` defines five objective conditions. `write-spec.md §3` restates them in workflow context. The criteria are falsifiable and complete.

### Can a contributor correctly create a change proposal?

**Yes.** `start-change.md` is clear and prescriptive. Required sections are enumerated.

**Minor friction:** proposal header format differs across old and new proposals (some use `A.`/`B.` lettered sections, others use `1.`/`2.` numbered sections). There is no canonical template for the proposal file itself.

### Can a contributor correctly execute tasks?

**Yes.** `start-task.md` and `implement-task.md` are among the strongest documents in the system. `install-cli-foundation/tasks.md` demonstrates this — it is extremely detailed with atomic steps and STOP conditions. Task execution appears reliable for well-formed task files.

## 5. Enforcement Strength Analysis

### Gates (all convention-based; no automation)

| Gate | Location | Strength |
|---|---|---|
| Spec required before feature proposal | `start-change.md` step 1 | Weak — convention only; never tested |
| Ready spec required before feature planning | `start-plan.md` | Weak — convention only; never tested |
| Tooling/foundation checklist at planning | `start-plan.md` + `tooling-changes.md` | Moderate — checklist is explicit; tested once (install-cli-foundation) |
| Probe-first for tooling task execution | `implement-task.md` | Moderate — clear rule; tested once |
| Status relationship rules | `change-artifacts.md` | Weak — violated by two existing changes; no enforcement |
| Docs-in-same-change | `implement-task.md` | Moderate — clear rule; generally followed |
| validate-docs checklist before PR | `validate-docs.md` | Weak — some items are ambiguous; checklist is manual |

### Weakest points

1. **Status reconciliation** — two changes currently violate the closure rule; the rule exists but is not enforced and was not applied retrospectively.
2. **Feature spec gate** — the most important SDD gate has never been exercised. Its correctness is theoretical.
3. **`validate-docs.md` item 5** (`docs/features/`) — ambiguous scope; may be skipped incorrectly or checked without knowing what to verify.
4. **Branch-per-change convention** — `git.md` prescribes feature branches. Evidence from commit history suggests changes were executed directly on `main`. The workflow document instructs branching but reality diverges.

## 6. Gaps and Risks

### Critical

None that block basic SDD usage for current change types (`sdd-system`, `tooling/foundation`).

### Important

**I1.** `install-cli-foundation/proposal.md` has Status `Draft (not started)` but `tasks.md` is `Complete`. This is an explicit closure rule violation. A reader cannot determine the change's state from its artifacts.

**I2.** `define-node-typescript-cli-foundation/tasks.md` has no `Status:` field and all definition-of-done checkboxes are `[ ]`. The work is complete by evidence (files exist), but the artifact does not reflect this. Misleads anyone reading the change folder.

**I3.** The feature spec gate (the primary SDD differentiation) has never been exercised. The first `feature` change will be the first real test. If the workflow has gaps, they will be discovered then, not now.

**I4.** `docs/features/_template/plan.md` has a task checklist that duplicates `tasks.md`. When a contributor creates a new feature, they may track tasks in two places or ignore one, creating inconsistency.

### Minor

**M1.** `strengthen-tooling-change-workflows/proposal.md` uses non-canonical type `SDD system improvement (no application code changes)`. Should be `sdd-system`.

**M2.** `define-node-typescript-cli-foundation/proposal.md` and `install-cli-foundation/proposal.md` use non-canonical status strings (`Draft (proposed)`, `Draft (not started)`). Should be `Draft`.

**M3.** `validate-docs.md` checklist item 5 (`docs/features/`) does not specify when it applies. For `sdd-system` changes this item is vacuously true or not applicable, but the checklist does not say so.

**M4.** Status relationship rules are duplicated across three files. The duplication is currently consistent but is a future maintenance risk.

**M5.** No canonical proposal template file exists. Older proposals use `A.`/`B.` sections; newer ones use `1.`/`2.` sections. A `_template/proposal.md` would reduce format drift.

## 7. Unnecessary Complexity

### 7.1 `docs/features/_template/plan.md` task tracking

The `plan.md` template has a `## Tasks` section with task-item checkboxes. Since `tasks.md` is now the canonical execution tracker, these checkboxes are redundant. They could be replaced with a pointer to `tasks.md`. Keeping both risks divergence.

### 7.2 `docs/features/` as a third documentation layer

The documentation layers are: spec (`sdd/specs/<topic>.md`) → proposal/tasks (`sdd/changes/`) → feature docs (`docs/features/<name>/feature.md` + `plan.md`). For a feature change, all three layers exist. Whether `docs/features/` adds value over the spec and proposal is untested — no feature has been fully implemented. If `docs/features/` mainly duplicates the spec's behavior description, it is overhead without clear benefit.

This isn't a finding to act on now (no feature exists to evaluate it against), but it is a complexity risk to watch.

### 7.3 `start-plan.md` document length

`start-plan.md` contains five distinct checklists: feature spec gate, change classification table, target stack check, agent-safety checklist, and tooling/foundation checklist. The document is long. While each section is legitimate, a contributor reading it for the first time faces high cognitive load. The target-stack check section in particular applies narrowly (output-generating changes) but is buried in a general-purpose planning document.

## 8. Overall Readiness Assessment

**Yes — with minor caveats**

### Reasoning

**Ready for:**
- Ongoing `sdd-system` changes (the entire change history is this type; the system works reliably).
- Ongoing `tooling/foundation` changes (the checklist-heavy model was refined by `strengthen-tooling-change-workflows` after one real execution failure; it is now solid).
- Beginning the first `feature` change, given the spec workflow now exists.

**Caveats:**
- Two historical changes have stale/violated status fields (I1, I2 above). These should be normalized before confusion spreads.
- The feature spec gate is architecturally sound but has zero track record. The first feature change is the true test.
- The branch convention in `git.md` appears to not be followed in practice (commit history on `main`). If PRs are required later, this gap will surface.
- `docs/features/_template/plan.md` needs its task section resolved before the first feature creates confusion.

## 9. Suggested Improvements (minimal, high-impact)

Listed in priority order. Each is a small, targeted fix.

**P1. Close the two stale changes (Important)**
- `install-cli-foundation`: set `proposal.md` Status to `Closed`.
- `define-node-typescript-cli-foundation`: set `tasks.md` Status to `Complete` and mark definition-of-done items `[x]`; set `proposal.md` Status to `Closed`.

**P2. Remove or replace the task checklist in `docs/features/_template/plan.md` (Important)**

- Eliminates the redundancy before the first feature is created.

**P3. Clarify `validate-docs.md` checklist item 5 (Minor)**
- Append: "(Required for `feature` changes only. Not applicable to `sdd-system`, `tooling/foundation`, or `fix` changes.)"
- Removes ambiguity without changing behavior.

**P4. Add a `_template/proposal.md` starter (Minor)**
- Create `sdd/changes/_template/proposal.md` with the canonical header fields and section numbering.
- Prevents format drift in future proposals without requiring a documentation rewrite.

**P5. Normalize stale type/status in `strengthen-tooling-change-workflows/proposal.md` (Minor)**
- Change type from `SDD system improvement (no application code changes)` to `sdd-system`.
- Opportunistic fix per the historical-migration policy already defined in `change-artifacts.md`.
